# GTM OS — プロダクトブリーフ

> GitHub リポジトリを繋ぐだけで、AI がコードを読んで UI をレンダリングし、
> **デモ動画とインタラクティブデモを同じフローから出力する**パイプライン。

位置づけ:[`docs/business-plan.md`](../business-plan.md) の 3 本柱のうち**ローンチ動画のプロダクト化**。
ロードマップ Phase 3(型のプロダクト化)に該当する。

## 1. 本当の差別化は「コードから描ける」ことではない

調べた結果、**当初の差別化の言い方だと弱くなる**ので、一段上げることを提案します。

### 競合の実態

| | 何をしているか | 弱点 |
| --- | --- | --- |
| **RepoClip** | コード解析(Gemini 2.5 Flash)→ 台本生成 → **AI 生成画像** + 合成ナレーション。約 5 分。GitHub Action あり | **本物の UI ではない**。プロダクトを見せていない |
| **Arcade / Supademo** | 人がブラウザ拡張で操作 → スクショ / 録画をキャプチャ | 人手が要る。**UI が変わったら作り直し** |
| **Storylane / Navattic** | **HTML クローン**。実 UI を高忠実度で複製 | 同上。人が触って取る。**作った瞬間から腐り始める** |
| **AIOProductOS Studio** | 動いているプロダクトを Playwright で録画 | **動いていないと撮れない** |

### ここから見えること

キャプチャ型(Arcade / Storylane / Navattic)は**忠実度では既に十分高い**。HTML クローンまでやっている。
だから「実 UI を見せられる」だけでは差別化になりません。**Navattic は既にやっている。**

**本当に誰も解いていない問題はこれです:**

> **デモは、作った瞬間から腐る。**
> UI を変えるたびに、人間がもう一度ブラウザを開いて、クリックして、撮り直す。
> だから世の中のプロダクトデモは、たいてい 3 ヶ月古い。

**GTM OS の差別化は「コードから描ける」ではなく、「マージのたびに再生成されるので、腐らない」。**

これはキャプチャ型が構造的に持てない性質です。人間が操作する前提である限り、CI には載せられない。

### 取るべきポジション

> **Demos as code. デモを CI に載せる。**
> プロダクトが変わったら、デモも変わる。人が撮り直さなくていい。

- 売り物は「動画を作ること」ではなく **「常に最新であること」**
- だから **GitHub Action / CI 連携が主機能**であって、おまけではない
- RepoClip も GitHub Action を出しているが、**出てくるのが AI 生成画像**なので同じ土俵にいない

**「動いていなくても撮れる」は残しますが、二番目の主張に下げる**ことを勧めます。一番目は「腐らない」。

## 2. 技術的な訂正 2 点

### 2-1. Playwright はネイティブアプリを操作できない

> 「SwiftUI、Jetpack Compose は…シミュレーター/エミュレーターを Playwright で操作する方式」

**Playwright は Web 専用**(Chromium / Firefox / WebKit)です。iOS シミュレータや Android エミュレータのネイティブ UI は操作できません。

正しい選択肢:

| プラットフォーム | ドライバ |
| --- | --- |
| Web | **Playwright** |
| iOS | **Maestro**(YAML でフロー記述、simulator 対応)/ XCUITest / Appium |
| Android | **Maestro** / UIAutomator / Appium |
| **macOS** | **XCUITest / Accessibility API**(シミュレータが存在しないので実機ランナーが要る) |

**Maestro を推奨**:iOS / Android を 1 つの記法で書けて、フローが YAML なので **AI が生成しやすい**。ここは GTM OS のパイプラインと相性が良い。

### 2-2. SwiftUI → React 変換は、忠実度のリスクが大きい

SwiftUI → React は**見た目の再現が想像よりずっと難しい**。VStack / HStack → flexbox は写せますが、写せないものが多い:

- SF Symbols、システムフォント、ダイナミックタイプ
- マテリアル / ブラー / vibrancy
- ナビゲーションのセマンティクス(NavigationStack、sheet、popover)
- スプリングアニメーション、ジェスチャ

**ローンチ動画で「実物と微妙に違う UI」を見せるのは、動画が無いより悪い。** 信用の問題になります。

**推奨**:iOS / Android は**シミュレータ / エミュレータ実行を第一手段**にする。
変換方式は「速いプレビュー」用の副手段に留め、**出力に必ず忠実度ラベルを付ける**(§4)。

## 3. 難度と差別化が逆相関している

これが最大の戦略的緊張です。

| | 実装難度 | 差別化 | 手段 |
| --- | --- | --- | --- |
| **Web** | **低** | **弱い** — Vercel の preview deploy + Playwright でほぼ再現可能 | build → headless render |
| iOS | 中 | 強い | simulator + Maestro |
| Android | 中 | 強い | emulator + Maestro |
| **macOS** | **高** | **最強** — 競合が誰もやっていない | 実機ランナー + XCUITest / Accessibility API |

**作りやすいところは差別化が弱く、差別化が強いところは作りにくい。**

Web は「常に最新の UI をコードから」がほぼコモディティです。preview deploy が既にそれをやっている。
だから **Web で証明し、ネイティブで勝つ**という順序になります。

### グループが既に持っている不当な優位

**macOS アプリを駆動・キャプチャするのに必要なのは Accessibility API。**
それは **SHOGUN の Memory Layer そのもの**です。

- SHOGUN は macOS Accessibility API で UI ツリーを受動的に読む技術を既に持っている
- GTM OS が macOS アプリを撮るには、まさに同じ技術が要る
- **競合はこれを持っていない。しかも一番難しいところ。**

「グループ横断で GTM 機能を持つと強い」の、最も具体的な実例になります。

## 4. 最大の難所はレンダリングではなく「状態とデータ」

コードから UI を描くところまでは、正直どうにでもなります。**問題はその UI が空っぽなこと。**

- ログインしていない
- データが 0 件
- API が返ってこない
- 空状態のプレースホルダしか映らない

**空の UI はデモになりません。** ここが実装工数の大半になります。

### 対処

| 手段 | 中身 |
| --- | --- |
| **E2E テストのフィクスチャを再利用** | 既にシードデータと認証が書かれている。**最も現実的** |
| シード生成 | AI がスキーマを読んで、それらしいデータを作る |
| API モック | 記録済みレスポンスを差し込む |
| 手動オーバーライド | どうしても要る値をユーザーが渡す |

**リポジトリに E2E テストがあるかどうかで、出力品質が大きく変わる。** これは製品仕様として明示すべき前提です。

---

## 5. キラーユースケース候補の抽出 — 信号の強い順

「AI がコードを読んで候補を出す」の中身。信号の強さには明確な序列があります。

| 順 | 情報源 | なぜ強いか |
| --- | --- | --- |
| **1** | **E2E テスト(Playwright / Cypress / Maestro)** | **既に記録されたユーザージャーニー**。セレクタも手順も揃っている。ほぼそのままデモになる |
| 2 | ルーティング / ナビゲーション定義 | 画面の全体像と階層 |
| 3 | アナリティクスのイベント定義 | **開発チームが何を重要と思っているか**が露出する |
| 4 | README / docs / 既存 LP のコピー | 本人たちの言葉での価値主張 |
| 5 | **git 履歴 / PR タイトル / CHANGELOG** | **アップデート動画の素材そのもの**。Before/After が自動で作れる |
| 6 | feature flags | 何が新しいか |

**1 が圧倒的です。** E2E テストがあるリポジトリなら、デモフローはほぼ無料で手に入る。
逆に言うと「E2E テストをそのままマーケ資産に変える」という言い方ができます。これは開発者に刺さる角度です。

## 6. アーキテクチャ(段階分解)

```
① Ingest      GitHub URL → clone / 権限
② Detect      プラットフォーム・フレームワーク・ビルド方法の判定
③ Build       ビルド + シードデータ + 認証の解決   ← ここが最重量(§4)
④ Understand  ユースケース候補の抽出(§5)→ ユーザーが選ぶ
⑤ Render      UI を起動して駆動(Playwright / Maestro / XCUITest)
⑥ Capture     ★ フレーム + 構造(DOM / AX ツリー)を両方保存
⑦ Compose     テンプレ適用(§7)
⑧ Emit        動画(多フォーマット)+ インタラクティブデモ
```

### ⑥ が製品の核

**「同じフローから動画とインタラクティブデモを両方出す」を成立させる条件は、キャプチャ段階でピクセルと構造を同時に取ること。**

- ピクセルだけ → 動画は作れるが、触れるデモは作れない
- 構造だけ → 触れるが、絵が出ない

Storylane / Navattic は HTML(構造)を取る。Arcade はピクセルを取る。
**両方取るのが GTM OS。** ここが「同じフローから 2 つ出力」の技術的な要です。

ネイティブでは「構造」= **アクセシビリティツリー**になります。これも SHOGUN の技術と同じ層。

## 7. 動画テンプレ

パターン 3 つは妥当です。**選択軸を「フェーズ」に固定する**のが分かりやすい。

| フェーズ | パターン | 尺 | 素材 |
| --- | --- | --- | --- |
| **ローンチ** | 問題提起 → 解決 → CTA | 60s | キラーユースケース 1 本 |
| **アップデート** | **Before / After** | 15〜30s | **git diff から自動生成できる** |
| **営業** | 機能デモ一本勝負 | 2〜3min | ユースケース複数 |

### 尺とフォーマットは必ず複数出す

- **15s**(X / Reels / Shorts)/ **60s**(ローンチ)/ **3min**(営業)
- **16:9 / 9:16 / 1:1** を同時書き出し

型 #01 の知見:X ではネイティブ動画 60 秒未満が最も伸び、**冒頭が不明瞭だと 73% が 15 秒未満で離脱**。
→ **テンプレに「最初の 3 秒で何が起きるか見せる」を構造として埋め込む。**

**アップデート動画が一番の勝ち筋かもしれません。** git diff から自動で Before/After が作れて、リリースのたびに走る。
「腐らない」というポジションと完全に一致するし、**継続課金の理由になる**(ローンチ動画は 1 回きり)。

## 8. 忠実度(Fidelity)を等級として持つ

ローンチ動画で嘘をつくと致命傷になります。**どのレベルで描いたかを製品として明示する。**

| 等級 | 中身 | 扱い |
| --- | --- | --- |
| **L0** | AI 生成画像 | **採用しない**(RepoClip の位置) |
| **L1** | 変換レンダリング(SwiftUI → React 等) | 「近似」と明示。社内 / プレビュー用途のみ |
| **L2** | 実ビルド・実レンダリング(Web build / simulator) | **標準** |
| **L3** | 実機・実データ | 最高。営業デモ向け |

**「この動画は L2 です」を出力に添える。** 忠実度を商品にする、という考え方です。競合が言えないことなので、そのまま差別化になります。

## 9. 共通テンプレのリポジトリ構成(案)

```
templates/
  devices/          Mac / iPhone / Android のフレーム SVG、影、反射
  backgrounds/      macOS 壁紙、グラデーション、無地
  cursor/           カーソル SVG、クリック波紋、移動イージング
  captions/         字幕スタイル、タイミング規則、フォント
  skeletons/
    launch.yml      問題提起 → 解決 → CTA
    before-after.yml
    feature.yml
  prompts/
    detect-usecase.md    キラーユースケース抽出
    write-script.md      台本
    pick-shots.md        どの画面をどの順で
  formats/          16:9 / 9:16 / 1:1、尺別の書き出し設定
```

**すべて Git で管理し、テンプレ自体もバージョニングする。**
「テンプレを更新したら、過去の全デモを再生成できる」が成立すると、これも腐らない側の性質になります。

## 10. 何から作るか

事業側のルール(**人力 2 回 → 手順化 → 3 回目で機械化**)をそのまま適用します。

| Phase | 中身 | 完了条件 |
| --- | --- | --- |
| **0** | **SHOGUN のローンチ動画を人力で作る** | 手順が全部記録されている |
| **0'** | もう 1 本、別プロダクトで人力 | 2 回目が 1 回目の 50% 工数 |
| **1** | **Web × ローンチパターンだけ**自動化 | GitHub URL → 60s 動画が出る |
| **2** | 同じキャプチャからインタラクティブデモ | ⑥ の二重キャプチャが動く |
| **3** | **macOS**(不当な優位のある領域) | XCUITest / AX ツリーで駆動できる |
| **4** | iOS / Android(Maestro) | |
| **5** | **アップデート動画の自動生成**(git diff → Before/After) | CI で毎リリース走る |

**Phase 0 の実案件は既に決まっています。**
[`shogunai-gtm-checklist.md`](../cases/shogunai-gtm-checklist.md) §6 に、画面録画 10〜15 カット・60 秒ローンチ動画・多フォーマット書き出しがタスクとして載っている。**あれが GTM OS の 1 人目の顧客**です。

「内製で証明していないものは売らない」という原則にも、そのまま乗ります。
