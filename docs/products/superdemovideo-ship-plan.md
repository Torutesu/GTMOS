# Superdemovideo — 出荷までに残っていること

2026-07-28 時点。実装は `product/superdemovideo/`。

---

## 1. 今できること(検証済み)

**自分たちで書いたフィクスチャ(Taskloop)に対しては、最初から最後まで通る。**

```
リポジトリを指す → 候補を 3 件提示 → 1 つ選ぶ → 動画 3 本 + クリックできるデモ
→ 公開 → コードを変更 → 再生成 → 変わった箇所の一覧 → 承認 → 同じ URL で中身が入れ替わる
```

`pnpm accept` がこれを 68 項目で自動検証する(mock モード、ネットワーク不要、API キー不要、約 4 分)。
ユニットテスト 103 件、`tsc --noEmit` クリーン。

出るもの:

| 成果物 | 状態 |
| --- | --- |
| 16:9 / 9:16 / 1:1 の mp4(H.264、30fps、22 秒) | 出る |
| poster.png(最初に製品が写るフレーム) | 出る |
| 字幕 en/ja(SRT)+ 英語は焼き込み | 出る |
| クリックできるデモ(3KB のプレイヤー) | 出る |
| 1 ファイル HTML のデモ(サーバー不要、外部通信ゼロ) | 出る |
| 鮮度バッジ(README に貼れる SVG) | 出る |

動かす手段:HTTP API、`sdv` コマンド、ブラウザの画面(4 ページ)。

## 3. 出荷を止めている問題(重い順)

**1 位:他人のリポジトリで動かない。**
9 本試して 18 件の不具合を直したが、まだ 1 本も動画に到達していない。
そして 18 件のうち、自分たちのフィクスチャで見つけられたものは 1 件も無い。
「動くものができた」と「動くと言える」の間に、この 18 件がそのまま入っている。

**2 位:知らない人のリポジトリを受け付けられない。**
`npm install` は任意のコードを実行する。今の実行環境ではそれがこのマシンの権限で走る。
自分たちのリポジトリなら問題ないが、他人から URL を受け取る形にはできない。

**3 位:候補の質が測れない。**
mock では常に決まった答えしか返らない。
「見せるべき機能を選ぶ」という中核の判断が、一度も本番で動いていない。

**4 位:動画とデモの見た目が食い違う。**
「動画とデモは同じ 1 回の記録から作るので食い違わない」が売り文句なのに、
再生時のダークモード判定で崩れる。

**5 位:出力を直せない。**
自動生成が 8 割正しくても、残り 2 割を直せないなら人は使わない。

## 4. 決めないといけないこと

**決定 1〜4 はすべて決着済み。**以下は決めた内容と、その根拠の記録。

### 決定 1:誰に出すか → **A → B → C の順(決定済み)**

| 案 | 内容 | 必要になるもの |
| --- | --- | --- |
| **A. 自社だけ** | SHOGUN のローンチ動画を Superdemovideo で作る | §3 の 1・3・4 だけ。安全性は問題にならない |
| **B. 人力サービス** | 顧客のリポジトリを預かり、こちらで回して成果物を渡す | A + 出力を直す手段(§2-2 の 4) |
| **C. セルフサーブ** | 利用者が自分で URL を入れて使う | A + B + Docker 分離 + GitHub 連携 + 認証 + 課金 |

C は A・B の上に積む形なので、**A → B → C の順に進めば手戻りは無い。**
逆に、最初から C を目指すと Docker とインフラに時間を使い、
**1 位の問題(他人のリポジトリで動かない)を先送りすることになる。**

→ **A → B → C で進める。**

### 決定 2:E2E テストを必須にするか → **必須にしない(決定済み)**

E2E テストがあると手に入るものは 4 つ。

| | 内容 | 無いときの代替 |
| --- | --- | --- |
| 1 | **ログイン済みの状態**(`storageState`) | **無い** |
| 2 | 解決することが分かっているセレクタ | ソースからの推測 |
| 3 | 「守る価値がある」と誰かが判断した手順 | ルート一覧からの推測 |
| 4 | UI 変更後の追随(チームが保守している) | 推測分は我々が保守する |

**1 だけが構造的な差。** `seed` がログイン状態を得る経路は `profile.e2e.storageStatePath` しかなく、
無ければログアウト状態でしか撮れない。ログインの内側が本体の製品では、それでは成立しない。

**必須にするメリット:** 品質を約束できる(tldraw の実測で候補 7 件が全部テスト由来、
無いリポジトリは全て 1 件)。ログインの内側を撮れる。セレクタ解決の事故が消える。
E2E を書く文化がある層は購買層と重なりやすい。

**必須にするデメリット:** 対象が狭まる。ただし実測 9 本中 1 本という数字は
**OSS のライブラリとフレームワークを選んだ結果**で、実際の顧客(SaaS プロダクト)の
採用率は測っていない。この数字を根拠にしてはいけない。
そして入口で断る形になり、試してもらえない。

**必須にしない理由:**

1. この判断が効くのは C(セルフサーブ)で見知らぬ人が来たとき。A と B では個別に判断できる
2. 必須にしなくても実質そうなる。ログインの内側が本体の製品では E2E 無しでは使えないので、
   顧客側が自然に絞られる。入口で断るより、使ってから
   「テストがあればこう変わる」と分かるほうがテストを書く動機になる

**ただし今の製品はそれを一切伝えていない。** E2E が無いとき UI は「候補 1 件」とだけ出し、
なぜ 1 件なのかも、ログインの内側が撮れないことも言わない。**これは直す(計画 §5 に追加)。**

### 決定 3:主商材は「動画」か「腐らないデモ」か → **両方(決定済み)**

動画のほうが分かりやすいので入口になり、同じ記録からデモを作る。
逆にデモを見せた相手に動画を渡す流れもある。

**実装上はすでにそうなっている。** 動画とデモは 1 回のキャプチャから両方出るので、
片方を作ってからもう片方を作る追加コストはゼロで、内容が食い違うこともない。

計画への影響は「どちらも落とさない」だけ。順番は変わらない。

### 決定 4:価格 → **当面考えない(決定済み)**

ビジネス側の設計は保留。技術側の判断材料が揃うまで着手しない。

## 5. 計画

### どの道でも必要(先にやる)

| 順 | やること | 終わったと言える条件 |
| --- | --- | --- |
| 1 | **他人のリポジトリで動画を 1 本出す** | Playwright テストを持つ実在アプリ 1 本で、`sdv init` から動画とデモまで到達する |
| 2 | 同じことを別の 2 本で繰り返す | 3 本中 2 本が到達する。落ちた 1 本は理由が説明できる |
| 3 | **本物の LLM で 1 回通す** | `ANTHROPIC_API_KEY` を入れて実行し、候補 3 件以上・費用がログに残る |
| 4 | ダークモードの食い違いを直す | 記録時のカラースキームで再生が固定され、動画とデモの色が一致する |
| 5 | **E2E が無いとき、何が制限されるかを画面で伝える** | 候補が少ない理由と、ログインの内側が撮れないことが、実行前に読める |

1 と 2 が最優先。**残りの判断材料が全部ここから出る。**
今わかっている次の壁は「build スクリプトがテストも走らせる場合の扱い」で、
これは修正ではなく判断が要る(テスト失敗を無視するか、より狭いスクリプトを選ぶか)。

5 は決定 2 の帰結。必須にしない以上、**何ができて何ができないかを製品が言う責任がある。**

### 決定 1 が A(自社だけ)なら

上の 1〜4 のあと:

| 順 | やること |
| --- | --- |
| 5 | SHOGUN のリポジトリで実際にローンチ動画を作る |
| 6 | 出てきた不満を記録する。ここで初めて「何を直せるべきか」が実データで分かる |

**ここで止めても事業として成立する** ── 型 #01 の成果物が自動化された、という状態。

### 決定 1 が B(人力サービス)なら

5〜6 に加えて:

| 順 | やること |
| --- | --- |
| 7 | 字幕を直す画面(テキストの差し替えだけ。再撮影はしない) |
| 8 | 画面の一部を隠す機能(顧客のデータが写る事故を防ぐ) |
| 9 | 運用手順書(受け取り方、確認項目、渡し方) |

### 決定 1 が C(セルフサーブ)なら

7〜9 に加えて:

| 順 | やること |
| --- | --- |
| 10 | **Docker 分離**。これが無い限り他人の URL を受け付けてはいけない |
| 11 | GitHub サインインと、リポジトリ接続 |
| 12 | GitHub Action での自動再生成と、PR への差分通知 |
| 13 | 利用者ごとの認証とデータ分離、保存先の外部化 |
| 14 | 課金 |

10 は妥協できない。**「他人のコードを実行する」を安全にする方法は他に無い。**
