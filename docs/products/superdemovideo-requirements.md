# Superdemovideo — 要件定義 v1.0

> **GitHub リポジトリを繋ぐと、コードから実 UI をレンダリングし、
> デモ動画とインタラクティブデモを同じキャプチャから生成・再生成し続けるプラットフォーム。**
>
> 一番目の主張:**デモは腐らない(Demos as code)**。マージ / リリースのたびに再生成される。
> 二番目の主張:プロダクトが動いていなくても、コードから撮れる。

- 背景・競合分析:[`superdemovideo-brief.md`](./superdemovideo-brief.md)
- ステータス:技術検証済み。本書は**プラットフォーム化のための要件**。
- 表記:**[M]** = MUST(v1 必須)/ **[S]** = SHOULD(v1 で入れたい)/ **[C]** = COULD(v2 以降)

---

## 0. プロダクト原則(全要件の上位規範)

| # | 原則 | 帰結 |
| --- | --- | --- |
| P1 | **鮮度が商品** | 単発生成ではなく再生成が主機能。CI 連携はおまけではなく核 |
| P2 | **実 UI 以外を出さない** | AI 生成画像・想像で描いた UI は出力に混ぜない(忠実度等級 §7) |
| P3 | **選抜は人、量は機械** | 候補・生成は AI が量産し、公開の判断は必ず人が押す |
| P4 | **顧客コードは商品ではなく預かり物** | コード保持は最小、CI モードではコードがそもそも外に出ない(§9) |
| P5 | **同じキャプチャから全出力** | 動画とインタラクティブデモは 1 回のキャプチャの 2 つのビュー |

## 1. 対象ユーザーと JTBD

| ペルソナ | 状況 | Job to be done |
| --- | --- | --- |
| **個人開発者 / OSS メンテナ** | 作るのは好き、見せるのが苦手。デモ作りが常に後回し | 「README とローンチ投稿に貼れる動画を、作業ゼロで持ちたい」 |
| **シード期のファウンダー** | PMM 不在。ローンチ・資金調達・営業で毎回デモが要る | 「LP・ピッチ・営業に使えるデモを常に最新に保ちたい」 |
| **DevRel / PMM(シリーズ A〜)** | リリースが速くてデモ制作が追いつかない | 「リリースノートに動画を毎回付けたい。撮り直し工数を消したい」 |

**優先順**:個人開発者 → シードファウンダー → DevRel。
理由:①配布ループ(§10.4)が個人開発者から始まる ②X での獲得(型 #01)と同じ層 ③要求水準が段階的に上がる。

## 2. スコープ

### v1(MVP)

- プラットフォーム:**Web アプリ(SPA / SSR / 静的)のみ**
- 入力:GitHub リポジトリ(public / private)
- 出力:**動画**(3 尺 × 3 アスペクト)+ **インタラクティブデモ**(ホスト型 + 埋め込み)
- 再生成:GitHub Action / webhook による自動再生成
- テンプレ:ローンチ型 / Before-After 型 / 機能デモ型

### v1.5

- デモ分析(視聴・完了・CTA)

### v2

- ブランチ型インタラクティブデモ、パーソナライズ、翻訳

### プラットフォーム対応(前倒しで実装済み)

当初は macOS を XCUITest、iOS / Android を Maestro で撮る想定だったが、
**どのアプリも HTML にしてからブラウザで撮る**方式に変えた。理由は 3 つ。

1. 実機・シミュレータ・Xcode / Gradle のツールチェーンが一切要らない
2. 撮影・合成・デモ書き出しの経路が Web と完全に同じになる(分岐が 1 箇所で済む)
3. SwiftUI・Compose・Android XML は**画面をラベル付きの階層として宣言している**ので、
   HTML と同じ形をしている。訳せる

代償は「実機のスクリーンショットではない」こと。実行時にしか現れない要素は出ない。
`fixtures/native-app` で `pnpm accept` が経路全体を検証している。

### 非スコープ(明示)

- AI 生成画像によるビジュアル(P2 違反。恒久的に非スコープ)
- 汎用動画エディタ(タイムライン細編集は Descript 等の領分。§6.6 の範囲まで)
- スクリーンレコーダー(人が録る機能は作らない。人が録るなら競合ツールでいい)
- デスクトップ Windows / Linux アプリ(需要が確認できるまで)

## 3. ユーザージャーニー(正常系)

### J1:初回(Time to First Demo)

```
① GitHub でサインイン(60秒)
② リポジトリを選ぶ → GitHub App インストール(90秒)
③ 解析が走る(バックグラウンド、2〜5分)
   → その間にブランドキット設定(ロゴ / 色 / フォント)を促す
④ ユースケース候補が 3〜7 件提示される
⑤ 1 件選ぶ + テンプレを選ぶ(既定:ローンチ型 60s)
⑥ 生成(5〜10分、進捗表示)
⑦ プレビュー → 軽い編集 → 「公開」
⑧ 共有 URL + 埋め込みコード + 動画ダウンロード
```

**目標:① から ⑧ まで 15 分以内(P50)/ 30 分以内(P90)。**

### J2:継続(ここが本体)

```
リリース(または main へのマージ)
 → 自動で再生成
 → 差分レポート付きでレビュー依頼が届く(「この 3 ステップで UI が変わりました」)
 → ワンクリック承認 → 公開中の全デモ・全埋め込みが更新される
 → 公開先の鮮度バッジが「v1.2.3 と同期」に更新される
```

### J3:失敗系(J1 の ③⑥ で必ず起きる)

- ビルド失敗 → **原因の要約 + 修正候補**を提示(「pnpm 9 が必要です」「.env.example に FOO が未定義」)。生ログも見られる
- データが空で画面が成立しない → シード戦略の選択肢を提示(§6.4)
- 候補が 1 件も出ない → ルート一覧から手動でフロー指定に誘導(§6.3)

**失敗系は例外処理ではなく主要 UX。** 接続されるリポジトリの相当数はすんなりビルドできない前提で設計する。

| ID | 要件 | 優先 |

## 6. 機能要件 — 生成と出力

### F6. Drive & Capture(駆動と二重キャプチャ)

| ID | 要件 | 優先 |
| --- | --- | --- |
| F6-1 | フロー実行は **Playwright スクリプト**として生成・保存(人が読める・直せる・差分が取れる) | [M] |
| F6-2 | **二重キャプチャ**:各ステップで (a) フレーム列(動画用)と (b) DOM スナップショット + 要素座標(インタラクティブデモ用)を同時取得 | [M] |
| F6-3 | カーソル移動・クリック・入力を**合成レイヤ**として記録(後からイージング・速度を変えられる) | [M] |
| F6-4 | ビューポート:デスクトップ(1440×900)+ モバイル(390×844)の 2 種を 1 Run で取得 | [M] |
| F6-5 | 待機の自動安定化(ネットワークアイドル・アニメーション完了を待ってから撮る。ガタつきを出さない) | [M] |
| F6-6 | 撮影に失敗したステップの特定と、そのステップだけの再実行 | [M] |
| F6-7 | **Electron**:renderer の HTML を配信し、preload の `contextBridge` が渡すはずの API を読み取って身代わりを注入する(実装済み) | [M] |
| F6-8 | **macOS / iOS / Android**:画面を宣言しているソース(SwiftUI・UIKit・Compose・Android XML)から HTML を生成して撮る(実装済み) | [M] |

## 7. 忠実度等級(出力の信頼性)

ブリーフ §8 を製品仕様化。**全出力のメタデータと共有ページに等級を明示する。**

| 等級 | 中身 | v1 での扱い |
| --- | --- | --- |
| L0 | AI 生成画像 | **存在しない**(非スコープ) |
| L1 | 変換レンダリング(SwiftUI→React 等) | **v1 では出さない**。導入時も「Preview」ラベル必須 |
| **L2** | 実ビルド・実レンダリング + シードデータ | **v1 の標準** |
| L3 | 実ビルド + 顧客提供の現実的データセット | [S] |

- FID-1 [M]:等級はユーザーが操作で上書きできない(信頼の根拠なので)
- FID-2 [M]:シードデータ使用時は共有ページ脚注に「サンプルデータ」と表示

## 9. 非機能要件

### セキュリティ(このプロダクトの信用の土台)

| ID | 要件 | 優先 |
| --- | --- | --- |
| SEC-1 | ビルドは使い捨てサンドボックス。Run 終了後にワークスペースを破棄。クローンの保持は再生成キャッシュ目的の暗号化保存のみ、**ユーザー設定で「保持しない」を選べる** | [M] |
| SEC-2 | **シークレットを預からない**:本番 env・API キー・DB 接続文字列の入力欄を作らない(F3-3 / F4-7) | [M] |
| SEC-3 | **CI モード**:Build〜Capture を**顧客の GitHub Actions ランナー内**で実行し、キャプチャ成果物(フレーム + 構造)だけをアップロードするモード。**コードが顧客環境から出ない** | [S] |
| SEC-4 | 成果物(動画・デモ)のアクセス制御:公開 / リンク限定 / ワークスペース限定 | [M] |
| SEC-5 | 削除要求から 30 日以内に全データ(成果物含む)を消去 | [M] |
| SEC-6 | SOC 2 Type I 相当の統制文書化(監査は需要が出てから) | [C] |

**SEC-3 は営業資産。** 「コードは預けたくない」という当然の反応への答えであり、DevRel / 企業層への展開条件。v1.5 で入れたい。

### 性能・信頼性

## 10. 課金・配布

### 10.1 課金軸

**プロジェクト(リポジトリ)単位のサブスクリプション**を主軸にする。
理由:価値の単位が「このプロダクトのデモが常に最新」であり、それはリポジトリに紐づく。再生成(継続価値)と課金(継続支払い)が一致する。

### 10.2 プラン(仮 — 価格は launch 前に要検証)

| プラン | 価格(仮) | 内容 |
| --- | --- | --- |
| **Free** | $0 | public リポジトリ 1 つ / 全出力に watermark + 「Made with Superdemovideo」/ 月 3 Run |
| **Pro** | $49/mo / プロジェクト | private 可 / watermark 無し / 自動再生成 / 全フォーマット / 月 50 Run |
| **Team** | $199/mo / ワークスペース | プロジェクト 5 / メンバー無制限 / CI モード / 分析 |

- BILL-1 [M]:Stripe。**7 日トライアル → 課金**(グループの型と揃える。無料枠は public 限定なので、hard paywall 原則とは両立)
- BILL-2 [M]:Run 超過は追加購入(従量)ではなく上位プラン誘導(v1 は課金体系を複雑にしない)

### 10.3 型 #01 との接続

自社の GTM チェックリスト(ShogunAI)と同じ計測規律を自分に適用する:

- **勝利条件(1 文)**:「**接続から 30 分以内に、共有可能なデモが 1 本公開されている**」
- North Star:**公開中かつ最新リリースと同期しているデモの数**(鮮度こそが価値なので、総生成数ではない)

### 10.4 配布ループ(プロダクトに埋め込む成長機構)

| ID | 仕組み | 優先 |
| --- | --- | --- |
| GROW-1 | Free の watermark と共有ページのフッター(「Made with Superdemovideo」→ LP) | [M] |
| GROW-2 | **README 鮮度バッジ**(F9-5)。OSS の README に貼られるほど流入が増える | [M] |
| GROW-3 | X 向け書き出しプリセット(60s / 字幕焼き込み / 冒頭 3 秒ルール)で「そのまま投稿できる」体験 | [M] |

## 11. 計測(プロダクト KPI)

| 指標 | 定義 | 位置づけ |
| --- | --- | --- |
| **活性化率** | 接続から 30 分以内に公開 1 本(勝利条件)に到達した割合 | **North Star 入口** |
| ビルド成功率 | 初回ビルド成功 / 接続(PERF-3) | **最大のプロダクトリスク指標** |
| 同期デモ数 | 公開中かつ最新版と同期しているデモ数 | **North Star** |
| 再生成承認率 | 自動再生成 → 承認された割合(低い = 再生成品質が低い) | 品質 |
| Day 7 転換率 | トライアル → 課金 | 収益 |
| 候補採用率 | 提示した候補のうち選ばれた割合(低い = Understand が外している) | 品質 |

## 12. v1 受け入れ基準(これが全部通ったら MVP 完成)

**シナリオ:Playwright テストを持つ public な Next.js リポジトリ**

1. GitHub サインイン → リポジトリ接続が 3 分以内に完了する
2. 5 分以内にユースケース候補が 3 件以上提示され、うち 1 件は E2E テスト由来である
3. 候補を 1 つ選び、ローンチ型 60s を指定 → 15 分以内に 16:9 と 9:16 の動画、およびインタラクティブデモが揃う
4. 動画の最初のショットはプロダクト画面であり、字幕が付いている
5. インタラクティブデモをクリックで最後まで進め、CTA が動作する
6. 吹き出しテキストを編集し、要素を 1 つマスクできる
7. リポジトリに UI 変更をマージ → GitHub Action が再生成 → 差分レビューが届く → 承認すると**同一 URL のまま**埋め込みが新版になる
8. 鮮度バッジが新バージョンを表示する
9. **E2E テストの無いリポジトリ**でも、ルート一覧から手動フローを組んで 3〜5 を達成できる
10. ビルドに失敗するリポジトリで、原因要約と修正候補が表示される
